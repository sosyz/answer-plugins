# 通行密钥连接器

[English](./README.md) | [中文](./README_CN.md)

> 使用通行密钥（Passkey，WebAuthn / FIDO2）登录 Apache Answer：用指纹、面容、屏幕锁或安全密钥代替密码。

本插件既是一个连接器（显示在其他登录按钮旁边，以及 **设置 > 账号 > 我的登录** 中），也是一个路由插件（提供运行 WebAuthn 流程的页面 `/connector-passkey-auth`）。

## 构建

```bash
./answer build --with github.com/apache/answer-plugins/connector-passkey
```

界面使用 pnpm 9.7.0 构建，即 Answer 核心锁定的版本（`ui/package.json` 中的 `packageManager`）。较新的 pnpm 可能要求先批准 esbuild 和 @swc/core 的构建脚本（`pnpm approve-builds`）后才能安装。

## 快速开始

管理员：

1. 带上本插件构建 Answer（见“构建”），然后重启。
2. 确认 **后台管理 > 设置 > 一般 > 网站网址** 是用户在浏览器中访问的 HTTPS 地址。通行密钥不能在普通 HTTP 下使用，`http://localhost` 除外。
3. 在 **后台管理 > 插件 > 已安装插件** 中启用 **通行密钥连接器**。不需要其他配置；可选配置项见“配置”。

用户：

1. 先用平常的方式登录，例如密码。
2. 打开 **设置 > 通行密钥连接器 > 管理通行密钥**（头像菜单 > **设置**），可以先填一个名称，点击 **添加通行密钥**，再点击 **创建新的通行密钥**。浏览器或设备会请你用指纹、面容、屏幕锁或安全密钥确认。
3. 下次在登录页点击 **连接到 通行密钥**，选择你的通行密钥即可；也可以直接在用户名输入框的自动填充里选择。

## 运行要求

- Apache Answer 2.0.2 或更高版本。插件依赖连接器的 OAuth `state`（登录和绑定两种意图），核心从 2.0.2 开始提供；在更早的版本上，每次登录都会因为缺少 state 而失败。（`go.mod` 中 `github.com/apache/answer` 的版本只是插件编译时所用的版本。）登录还依赖核心 `ConnectorLogin` 把新生成的 state 交给连接器的方式（见“登录”，2.0.2 到当前版本完全相同）。这里的大多数改动都会让登录以 `state_unverified` 失败，而不是放行；但如果将来的核心在读取到空的 `state` 查询参数后，把调用方提供的 state 写进 URL，这项检查就会失效。因此升级核心时请重新确认；根本的修复需要核心配合（见“剩余风险”）。
- HTTPS 的网站网址。浏览器只允许在安全来源上使用 WebAuthn，唯一的例外是用于开发的 `http://localhost`。
- 支持通行密钥的浏览器。浏览器支持时会使用条件式界面（在用户名自动填充中提供通行密钥）。

## 配置

所有字段都是可选的。留空的字段会从网站网址（**后台管理 > 设置 > 一般**）推导，所以网站网址正确的站点无需任何配置即可使用。

| 字段 | 留空时的默认值 | 规则 |
| --- | --- | --- |
| 依赖方名称（`rp_name`） | 网站网址的主机名 | 创建通行密钥时由浏览器或密码管理器显示。 |
| 依赖方 ID（`rp_id`） | 网站网址的主机名 | 纯域名，例如 `example.com`，或 `localhost`。不能带协议、端口、路径，也不能是 IP 地址。 |
| 允许的来源（`rp_origins`） | 网站网址的来源（`scheme://host[:port]`） | 用逗号或换行分隔。每个来源都必须使用 `https`（`localhost` 可以用 `http`），不能带路径、查询参数或片段，并且必须在依赖方 ID 或其子域名下。 |

说明：

- 带子路径的网站网址也能正确推导出依赖方 ID 和来源：`https://example.com/community` 得到依赖方 ID `example.com` 和来源 `https://example.com`。页面会从自身的 URL 推出基础路径（见“限制”）。
- 部署在反向代理后面时，网站网址必须是用户在浏览器中看到的公开地址，否则来源校验会失败。
- 保存时会校验设置，无效的设置会被拒绝。如果请求时无法解析出设置（例如既没有网站网址也没有显式配置），接口返回 `503 not_configured`。启动时已不再有效的已存设置（例如更改网站网址之后）会被保留并显示在后台表单中，接口返回 `503 not_configured`，直到修正并重新保存。
- **更改依赖方 ID 会让所有已有的通行密钥失效。** 认证器把通行密钥绑定在依赖方 ID 上，用户需要重新创建。

## 流程

### 登录

1. 用户在 Answer 登录页点击 **通行密钥**。核心创建一个登录用的 `state`，连接器跳转到 `/connector-passkey-auth?state=…&state_proof=…`。
2. 用户选择一个通行密钥（点击按钮，或选择浏览器的自动填充建议）。
3. 服务端验证断言，生成一个与该 state 绑定的一次性 token，并返回核心的回调地址 `/answer/api/v1/connector/redirect/passkey?state=…&token=…`。
4. 核心通过连接器兑换 token，完成登录。

`state_proof` 是对 state 计算的 HMAC，密钥由插件存储的密钥经 HKDF-SHA256 派生。连接器只会给核心刚为本次请求生成的 state 加上它，绝不会给调用方提供的 state（例如绑定用的 state，或从链接里复制来的 state）加上。`login/begin` 会拒绝没有有效证明的 state（`400 state_unverified`），因此携带其他账号绑定 state 的伪造链接，无法被用来登录、进而把访问者的通行密钥关联到那个账号。这项检查在服务端进行，不依赖浏览器存储。证明本身不会过期，state 被使用后也仍然有效；这没有危害，因为它只可能对应登录用的 state。

通行密钥只有关联到某个已有账号之后（见下文），才能登录该账号。用尚未关联的通行密钥登录，会进入核心为外部登录准备的新建账号流程。要在已有账号上使用通行密钥，请先在 **我的登录** 中关联。

同一个 Answer 用户的所有通行密钥共用一个身份（用户句柄），所以关联是按账号而不是按通行密钥进行的。如果一个未关联的通行密钥走完了核心的新建账号流程，这个身份就会关联到新账号：此后原用户的所有通行密钥都会登录到新账号，并且在新账号解除通行密钥关联之前，无法再把它们关联回原账号。

### 把通行密钥关联到账号

关联始终通过核心的绑定意图完成。关联时页面会忽略自身 URL 中的 `state`：每次认证之前，它都会向核心请求一个为当前登录用户生成的绑定 state（`GET /answer/api/v1/connector/user/info`）。未登录的访问者只能使用带有有效 `state_proof` 的 state 登录（见“登录”）。因此，携带其他账号绑定 state 的伪造链接，无法把访问者的通行密钥关联到那个账号。

1. 管理页上的 **关联通行密钥** / **添加通行密钥** 会打开 `/connector-passkey-auth?mode=bind`（带上输入的名称，用于新建的通行密钥）。从 **设置 > 账号 > 我的登录** 中通行密钥旁的连接按钮进入时，URL 会带着核心的 `?state=…`，页面会忽略它。无论从哪里进入，页面都会把 `state`、`state_proof` 和 `name` 从地址栏中移除。
2. 用户创建一个新的通行密钥，或验证一个已有的通行密钥。认证开始前，页面会获取核心为当前登录用户生成的绑定 state。
3. 服务端验证后，返回带有与该 state 绑定的一次性 token 的核心回调地址。
4. 核心兑换 token，把通行密钥身份关联到账号，然后回到账号设置页。

### 管理

**设置 > 通行密钥连接器 > 管理通行密钥**（头像菜单 > **设置**）（或 `/connector-passkey-auth?mode=manage`）列出当前登录用户的通行密钥，可以添加、重命名和删除。每个用户最多 20 个通行密钥。对于已关联通行密钥的账号，或无法确认关联状态时，页面不允许删除最后一个通行密钥：请先在 **我的登录** 中解除通行密钥的关联。如果通行密钥是某个无密码账号唯一的登录方式，核心会拒绝解除关联，所以账号不会因此被锁在外面。这条规则由页面执行；插件 API 没有提供让服务端读取核心绑定状态的途径。

## 安全说明

- **不向核心发送邮箱或个人资料。** 连接器只返回一个不透明的外部 ID（WebAuthn 用户句柄，32 个随机字节），因此核心永远不会按邮箱自动关联账号。账号只能通过绑定 state 关联。
- **跳转地址由服务端构造。** 页面从不从查询参数中读取跳转目标；完成接口返回的核心回调地址由网站网址构造。
- **登录 token** 是随机的，首次兑换后即删除，有效期 2 分钟，只以 SHA-256 哈希形式存储，并且只能与生成它时对应的核心 state 一起兑换（常量时间比较）。
- **认证状态不在服务端保存。** 开始接口返回一个用 AES-256-GCM 加密封装的不透明会话（密钥由插件 KV 中只存一次的密钥派生）。会话 5 分钟后过期，并与用途、用户和用户句柄绑定。该密钥在启动时创建（失败时在首次使用时创建），因此在加密验证成功之前，未登录的请求不会向数据库写入任何内容。（已登录的请求会写入：`register/begin` 会创建用户句柄，重命名和删除会直接写入。）
- **防重放。** 用过的挑战会在同一个事务中与凭据更新和 token 一起记录，保留到会话过期之后。在第一个请求完成后到达的重放会被拒绝；与第一个请求同时竞争的重放见“剩余风险”。
- **每次认证都要求用户验证和可发现凭据**，服务端会强制执行认证超时。
- **Attestation 为 `none`。** 由于没有可用于评估的元数据（MDS）策略，不请求 attestation 声明。
- **克隆检测直接拒绝。** 签名计数回退时拒绝登录，且不写入任何数据。每次使用都会更新备份标志和计数。
- **写入凭据前会检查凭据 ID 在所有用户之间唯一**（WebAuthn §7.1 第 22 步）；并发注册的情况见“剩余风险”。凭据的所有者取自已验证的记录，绝不取自客户端输入。
- **解除关联和删除相互独立。** 在 **我的登录** 中解除通行密钥的关联不会删除通行密钥，删除通行密钥也不会解除关联（例外是页面不允许删除已关联账号的最后一个通行密钥，见“管理”）。解除关联后要再次使用通行密钥，请在 **我的登录** 中重新关联。
- **剩余风险。**
  - 多实例下的并发请求：在同一个进程内，针对同一个挑战或 token 的完成和兑换请求会被串行化（恰好一个成功）；凭据 ID 唯一性检查、20 个上限检查与写入，以及同一个通行密钥的重命名或删除与登录，也都会被串行化；登录在写入前会重新读取通行密钥，所以已删除的通行密钥不会被写回，重命名或更新的计数也不会被改回旧值。在多个 Answer 实例之间，这些竞争仍然存在，因为已用挑战检查和唯一性检查在事务之前进行，而 `KVOperator.Set` 是“存在则更新，否则插入”：在另一个实例上与第一个请求竞争的重放请求，在 PostgreSQL 和 SQLite 上可能生成第二个登录 token（MySQL 的唯一索引会拒绝其中一个）；同一个 token 的两次同时兑换可能都成功；同一用户的并发注册可能超过 20 个上限。能检测到的失败事务会报告为 `session_invalid`（重复注册时为 `credential_exists`）。
  - 用户句柄创建：同一用户的两个首次 `register/begin` 同时发生时，可能互相覆盖用户句柄（后写入的生效）；失败的一方会以 `session_invalid` 结束，用户重试即可。
  - 两个实例在同一时刻首次启动时，可能都创建会话密钥（后写入的生效）；在失败实例上开始的认证会以 `session_invalid` 结束并重试。
  - 利用上述任何一项，都需要在毫秒级时间内拿到受害者本人的断言、token 或请求。多实例的情况无法在插件内解决，因为核心的 `KVOperator` 没有条件插入、比较后删除或行锁。向上游的建议：给 `KVOperator` 增加只插入的 `Set`（键已存在时失败）和比较后删除的 `Del`（报告是否删除了行）。
  - 绑定 state 泄露：插件看不到 state 属于谁，而核心绑定时使用 state 记录的用户，不检查浏览器当前的会话。任何人拿到某个用户仍然有效的绑定 state（5 分钟）后，都能把自己的通行密钥关联到该用户的账号。插件自身的关联流程从不把绑定 state 放进 URL：它在每次认证前才获取。核心 **我的登录** 中的连接链接仍然带着 state；绑定页面会把它从地址栏和历史记录中移除，并且从不使用它，但它仍可能在别处泄露（例如代理日志）。所有连接器都有同样的问题；根本的修复是让核心的 `ConnectorRedirect` 比较 state 的用户与当前登录用户，或把 state 的意图和所有者提供给连接器。
  - 核心 state 流程固有的登录 CSRF：核心的 state 没有与发起流程的浏览器绑定，攻击者可以用自己的通行密钥完成一次登录，再诱使未登录的受害者打开得到的回调地址，让受害者登录到攻击者的账号。所有连接器都存在这个问题；要解决，需要核心把 state 与浏览器会话绑定（例如使用 cookie）。

## KV 存储结构

所有数据都存储在 `plugin_kv_storage` 表中，插件标识为 `passkey_connector`。KV 缓存已禁用，每次读取都会访问数据库。

| 分组 | 键 | 值 |
| --- | --- | --- |
| `secret` | `ceremony_key` | 32 个随机字节的 base64url。AES-256-GCM 会话密钥和 `state_proof` 的 HMAC 密钥都用 HKDF-SHA256 从它派生。在启动时创建，失败时在首次使用时创建。 |
| `user_handle` | Answer 用户 ID | 32 个随机字节的 base64url：即 WebAuthn 的 `user.id`，也是核心中的外部 ID。在首次 `register/begin` 时创建，即使那次认证没有完成。 |
| `credential` | base64url(SHA-256(凭据 ID)) | JSON：`user_handle`、`name`、`created_at`、`last_used_at`，以及完整的 go-webauthn `credential` 记录（公钥、标志、计数、传输方式、attestation）。同时充当全局的凭据 ID 唯一索引。 |
| `user_credential:<handle>` | base64url(SHA-256(凭据 ID)) | `1`（归属关系，用于列出）。两行都存在时，凭据才算存在。 |
| `consumed_challenge` | 挑战 | 过期时间（Unix 秒）。过期后清理（每个进程每分钟最多一次，每次每个分组最多 1000 行）。 |
| `login_token` | base64url(SHA-256(token)) | JSON：`external_id`、`state`、`expires_at`。兑换时删除，过期后按与 `consumed_challenge` 相同的方式清理。 |

凭据 ID 经过哈希，以便键能放进 128 个字符的键列（原始 ID 最长可达 1023 字节）。

## 限制

- 在开启了 **需要登录** 的站点上，核心的路由守卫会阻止匿名访问 `/connector-passkey-auth`，因此无法使用通行密钥登录。
- 核心会把过期或未知的绑定 state 当作登录 state 处理：关联操作如果超过了核心 state 的有效期，会变成一次登录尝试。请从 **我的登录** 重新开始关联。
- 页面从自身 URL 推出界面的基础路径（`/connector-passkey-auth` 之前的部分），并认为接口位于同一前缀下（`<base>/answer/api/v1`），这与核心构造所有连接器 URL 的方式一致。`ui.base_url`、接口基础路径和网站网址的路径必须一致；核心的连接器不支持单独的接口基础路径。子路径部署已做处理，但尚未经过端到端测试。
- 当界面由 CDN 提供时（例如 `cdn-s3` 或 `cdn-aliyun` 插件），插件的模块脚本以 CORS 模式加载，CDN 必须为本站点返回 `Access-Control-Allow-Origin`。见 [cdn-s3](../cdn-s3/README.md) 和 [cdn-aliyun](../cdn-aliyun/README.md) README 中的 CORS 部分。
- 插件 API 没有提供获取当前登录用户的方法，所以需要登录的接口会读取核心鉴权中间件存放在请求上下文中的用户 ID（一个内部键）。如果将来的核心重命名或改变了它的结构，这些接口会返回 `401`，插件会记录一条指出原因的错误日志。

### 建议核心做的改动

以下改动可以消除上面剩余的限制和风险：

- 提供公开的 `plugin` 方法：一个返回当前登录用户 ID，另一个告诉连接器某个用户是否已与其关联（这样由服务端而不只是页面来拒绝删除已关联账号的最后一个通行密钥）。
- 让 `ConnectorRedirect` 比较绑定 state 的用户与当前登录用户，或把 state 的意图和所有者提供给连接器；并把 state 与浏览器会话绑定，以解决登录 CSRF。
- 为多实例部署，给 `KVOperator` 增加只插入的 `Set` 和比较后删除的 `Del`。
